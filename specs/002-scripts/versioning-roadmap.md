# Script Versioning — Implementation Roadmap

**Created**: 2026-04-23
**Status**: Proposed
**Depends on**: spec 002-scripts (current), spec 009-collaboration (future)

## Current State

| Aspect | Status | Detail |
|---|---|---|
| `contentVersion` field on ScriptModel | Exists, unused | Set to `1` on creation, never incremented |
| `VersionedEntity` base class | Exists for KB entities | ScriptModel extends only `RequiredTimeStamps` |
| Version history storage | Missing | Content is overwritten in-place on every save |
| Conflict detection | Missing | No optimistic concurrency on `saveContent` |
| Version API procedures | Missing | No contract endpoints for list/get/restore |
| UI version controls | Missing | Toolbar has no version dropdown |
| Content format | Tiptap JSON (serialized string) | Stored in `script.content` field |
| Save mechanism | 300ms debounce autosave | `saveScriptContent` overwrites content, returns `lastEditedAt` |

## Tiptap Versioning Landscape — What's Available

### Option A: Tiptap Collaboration Snapshots (Cloud/Enterprise)
Tiptap's **Collaboration Platform** offers a managed versioning layer:
- **Snapshot extension**: Captures document state at intervals or manually. Users can browse and restore snapshots.
- **Snapshot Compare**: Visual diff between two versions with author attribution.
- **REST API**: `POST /versions` to create, `GET /versions` to list, `POST /versions/:id/revertTo` to restore.
- **Yjs-based**: All edits stored as Yjs updates; versions are binary snapshots in Yjs format.

**Verdict: Not applicable to Kaeri.** The Snapshot/Compare features require Tiptap's managed Cloud documents (starting at $49/mo for the Start plan). Kaeri stores content as serialized Tiptap JSON in MongoDB, not as Yjs documents in Tiptap Cloud. Adopting this path would require migrating to the Tiptap Collaboration provider with Yjs sync, a Hocuspocus backend, and a paid subscription—far beyond the scope of a versioning feature.

### Option B: ProseMirror History Extension (Already Used)
Kaeri already imports `@tiptap/extension-history` which wraps ProseMirror's `prosemirror-history`. This provides **session-level undo/redo** (Ctrl+Z / Ctrl+Shift+Z) using an in-memory transaction stack. It does **not persist** across page reloads or provide named versions.

**Verdict: Useful for in-session undo/redo (already working). Not a versioning solution.**

### Option C: Self-Hosted Version Snapshots in MongoDB (Recommended)
Build a lightweight version history system inside the existing stack:
- On each significant save, store a snapshot of the Tiptap JSON content alongside metadata.
- Snapshots live in a dedicated `script_versions` MongoDB collection.
- A contract procedure lets users list, preview, and restore versions.
- Comparison (diff) can be done at the JSON structural level or rendered visually in the editor.

**Verdict: Best fit for Kaeri's architecture—no new dependencies, no paid services, full control.**

## Implementation Phases

### Phase 1: Backend Version Storage
**Goal**: Every meaningful content save creates a version snapshot in MongoDB.

#### 1.1 — ScriptVersion Model

Create `apps/server/src/db/models/script-version.model.ts`:

```
ScriptVersionClass
├── _id: string (ObjectIdString)
├── scriptId: string (indexed)
├── version: number (auto-incremented per script)
├── content: string (full Tiptap JSON snapshot)
├── contentHash: string (SHA-256 of content, for dedup)
├── createdBy: string (userId)
├── createdAt: Date
├── name?: string (user-assigned label, e.g. "Draft 2")
├── autoGenerated: boolean (true = autosave, false = manual)
└── metadata?: { wordCount?: number, blockCount?: number }
```

Compound index: `{ scriptId: 1, version: -1 }` for efficient list queries.
Unique index: `{ scriptId: 1, contentHash: 1 }` to prevent duplicate snapshot content.

#### 1.2 — Extend ScriptModel

- Make ScriptModel extend `VersionedEntity` to gain `_version`, `_lastModifiedBy`, `_lastModifiedAt`.
- Repurpose the existing `contentVersion` field as the authoritative version counter (or migrate to `_version` and drop `contentVersion`).

#### 1.3 — Version Creation Strategy

Not every autosave keystroke should create a version. Strategy:

| Trigger | Creates Version? | `autoGenerated` |
|---|---|---|
| Autosave (300ms debounce) | **No** — updates `script.content` in-place as today | — |
| Content differs from last version after inactivity (e.g. 5 min idle or tab blur) | **Yes** | `true` |
| Manual "Save Version" action from UI | **Yes** | `false` |
| Before restoring an older version | **Yes** (safety snapshot) | `true` |
| Script export (PDF) | **Yes** | `true` |

Use the `contentHash` unique index to skip creating a version if content hasn't actually changed since the last snapshot.

**Retention policy**: Keep the last N versions per script (e.g. 50 auto-generated + unlimited manual). Enforce via a TTL-based cleanup job or on-create pruning.

#### 1.4 — ScriptsService Changes

Add methods to `ScriptsService`:

```
createVersion(scriptId, userId, options?: { name?: string })
  → Snapshots current content into script_versions collection

listVersions(scriptId, limit, offset)
  → Returns paginated version summaries (id, version, name, createdAt, createdBy, autoGenerated)

getVersion(scriptId, versionId)
  → Returns full version content

restoreVersion(scriptId, versionId, userId)
  → Creates safety snapshot of current state, then overwrites script.content with version content

deleteVersion(scriptId, versionId)
  → Soft-delete or hard-delete a named version
```

Update `saveContent()`:
- After saving content, check if a version snapshot should be auto-created (time-based or content-diff threshold).
- Increment `_version` on every save.

### Phase 2: Contract & Router

#### 2.1 — New Error Codes

Add to `packages/shared/src/enums/errors.enums.ts`:

```
SCRIPT_VERSION_NOT_FOUND
SCRIPT_VERSION_LIMIT_REACHED
SCRIPT_CONTENT_UNCHANGED
```

#### 2.2 — Contract Procedures

Add to `packages/shared/src/contract/scripts.contract.ts`:

```
listScriptVersions
  path: /versions/list, method: GET
  input: { scriptId, limit?, offset? }
  output: { items: ScriptVersionSummary[], total: number }

getScriptVersion
  path: /versions/get, method: GET
  input: { scriptId, versionId }
  output: ScriptVersion (full content)

createScriptVersion
  path: /versions/create, method: POST
  input: { scriptId, name? }
  output: ScriptVersionSummary

restoreScriptVersion
  path: /versions/restore, method: POST
  input: { scriptId, versionId }
  output: { restoredVersion: number, safetySnapshotId: string }

deleteScriptVersion
  path: /versions/delete, method: DELETE
  input: { scriptId, versionId }
  output: { success: boolean }
```

New Zod schemas:

```
scriptVersionSummarySchema: { _id, scriptId, version, name?, createdBy, createdAt, autoGenerated, metadata? }
scriptVersionSchema: scriptVersionSummarySchema + { content }
```

#### 2.3 — Router Handlers

Add version handlers to `scriptsRouter` (or create a dedicated `scriptVersionsRouter`), wiring to the new service methods via `contentProtected`.

### Phase 3: Frontend — Version Panel & Restore Flow

#### 3.1 — Query & Mutation Hooks

```
useScriptVersions(scriptId)           → queryOptions for listScriptVersions
useScriptVersion(scriptId, versionId) → queryOptions for getScriptVersion
useCreateScriptVersion()              → mutationOptions for createScriptVersion
useRestoreScriptVersion()             → mutationOptions with optimistic update
useDeleteScriptVersion()              → mutationOptions
```

#### 3.2 — Version History Panel

Add a "Version History" panel accessible from the editor toolbar (or as a tab in the right-side panel alongside Knowledge Base / Canvas):

- **Version list**: Scrollable list showing version number, name (if any), timestamp, author, auto/manual badge.
- **Preview mode**: Clicking a version loads it into a **read-only** editor instance (disable all extensions except rendering). Show a banner: "Viewing version N — [Restore this version] [Back to current]".
- **Create version button**: "Save as version" with optional name input.
- **Restore confirmation**: Dialog confirming restore with note that current content will be safety-snapshotted first.

#### 3.3 — Auto-Version Triggers (Client-Side)

Implement idle detection in the editor component:
- Track last keystroke time.
- On tab blur or 5 minutes of inactivity after changes, call `createScriptVersion` (auto-generated).
- Use the `contentHash` dedup on the backend to avoid redundant snapshots.

#### 3.4 — Toolbar Integration

Update `EditorToolbar` to add a version indicator (e.g. "v12 · saved 2m ago") and a dropdown/button to open the version panel.

---

### Phase 4: Version Diffing (Stretch Goal)

#### 4.1 — Structural Diff

Since content is Tiptap JSON, a structural diff can compare two document trees:
- Identify inserted, deleted, and modified blocks.
- Map block types (scene-heading, action, etc.) to show meaningful change descriptions (e.g. "Scene heading added: INT. OFFICE - NIGHT").

Libraries to consider:
- `jsondiffpatch` — structural JSON diffing with delta output
- `diff` (npm) — text-level diffing on serialized content
- Custom tree diff on the Tiptap `doc.content` array, matching blocks by position and type

#### 4.2 — Visual Diff in Editor

Render a read-only "compare" view with:
- Green highlights for additions
- Red highlights/strikethrough for deletions
- Side-by-side or inline toggle

This mirrors what Tiptap's paid Snapshot Compare does, but built using the existing editor rendering with custom decorations.

## Key Design Decisions to Make

| Decision | Options | Recommendation |
|---|---|---|
| **Version granularity** | Every save vs. time-gated vs. manual-only | Hybrid: autosave updates in-place, auto-versions on idle/blur, manual versions on demand |
| **Storage format** | Full content snapshot vs. Yjs deltas vs. JSON diff patches | Full content snapshot — simpler, enables direct previews, storage is cheap |
| **Retention limit** | Unlimited vs. cap per script | Cap auto-generated (50), unlimited manual. Prune oldest auto-generated on overflow |
| **Version numbering** | Global counter vs. per-script sequential | Per-script sequential (1, 2, 3...) for user-friendly display |
| **Extend VersionedEntity?** | Use VersionedEntity base class vs. standalone fields | Use VersionedEntity for consistency with KB entities, but note it tracks optimistic concurrency (`_version`), not document history |
| **Separate router?** | Nest under `/scripts/versions/*` vs. new top-level router | Nest under scripts — these are script sub-resources |
| **Collaboration impact** | Design for single-user now vs. CRDT-ready | Single-user now. If spec 009 (collaboration) adopts Yjs/Hocuspocus later, version snapshots can be migrated to Yjs format |

## Non-Goals for This Roadmap

- **Real-time collaboration** — Covered by spec 009-collaboration.
- **Branch/merge workflows** — Over-engineered for a screenplay authoring tool.
- **Tiptap Cloud integration** — Requires paid subscription and architectural migration to Yjs sync.
- **Track Changes / suggestion mode** — Separate Tiptap paid extension, not part of versioning.
- **Versioning of script metadata** (title, authors, genre) — Only content versions are tracked.
